# IGSH-252 Sync 5: live sync of tabs, workspaces and settings across N laptops

Base: zigshell `origin/master` bf7ac4c (APP_VERSION 0.28.652). Local `master` is 16 commits behind, and every anchor below is at `origin/master`. Server: `/home/valentin/projects/multiprompt-android/worker` (origin/main a4a7678). Two decisions from Valentin are folded in: (1) mirror everything that isn't machine-specific, live, like browser-profile sync, with only a first switch-on per laptop; (2) design for N laptops.

## 1. Decisions
1. **Server and encryption:** keep sync.multiprompt.dev (Worker + D1) and the Sync 3/4 vault key. Every record is encrypted on the laptop with `sync_protocol.sealEntity` (sync_protocol.zig:134). The server stores opaque ids and ciphertext only.
2. **How "live" works:** push on change (500 ms debounce, `POST /batch`) plus a long-poll pull (`GET /changes?after=<seq>&wait=25`), which is one open request that returns as soon as something changes. Typical latency is 1–3 s, with one idle request per 25 s (55 s when saving power). No WebSocket or Durable Object in v1; a Durable Object can replace the server-side wait later with no client change.
3. **Server additions:** an account-wide change sequence, batch push, and per-laptop device keys. The existing `/records` and `/vault` endpoints are unchanged.
4. **Records and conflicts:** one record per tab, workspace, group and setting. The server's per-record revision is the only ordering authority. On a conflict (HTTP 409) the laptop does a per-field 3-way merge (last-synced base vs local vs server). No clocks decide conflicts, so it works for N laptops.
5. **Change detection:** after any `saveSession()` or `publishInboxState()`, the app projects its in-memory state into records, hashes them and pushes the diff. There is no operation log, and offline edits and crashes recover naturally.
6. **Remote tabs:** they arrive as parked placeholders and attach only when opened. A remote close closes only the local ssh client.
7. **Sync by default:** everything not machine-specific mirrors. There is one fixed per-machine list (section 4.1), and the opt-in is a one-time switch per laptop.

## 3. Transport and storage
### 3.1 Worker changes
Migration `0003`:
```sql
ALTER TABLE sync_entity ADD COLUMN seq INTEGER NOT NULL DEFAULT 0;
ALTER TABLE sync_entity ADD COLUMN device_id TEXT;
CREATE INDEX sync_entity_seq ON sync_entity (account_id, seq);
CREATE TABLE sync_account (account_id TEXT PRIMARY KEY, head INTEGER NOT NULL, paused INTEGER NOT NULL DEFAULT 0);
CREATE TABLE sync_device (device_id TEXT PRIMARY KEY, account_id TEXT NOT NULL, secret_hash TEXT NOT NULL,
  created_at TEXT NOT NULL, last_seen_at TEXT, acked_seq INTEGER NOT NULL DEFAULT 0, revoked_at TEXT);
```

**Device endpoints:**
- `POST /devices` (Cloudflare Access bearer only) returns `{deviceId, secret, accountId}`. The secret is 32 random bytes; the server stores its SHA-256.
- `GET /devices` lists devices; `DELETE /devices/:id` revokes one.

**Device auth:** `Authorization: Device <id>.<secret>` is accepted on `/changes`, `/batch`, `/records`, `GET /vault` and `/devices`. Revoked keys get 401. `last_seen_at` updates at most every 10 min.

**Change feed:** `GET /changes?after=&wait=0..55&limit=1..500` returns `{head, accountId, more, changes:[{seq, recordId, entityId, revision, tombstone, payload}]}` across all record ids.
- When there are no changes, the Worker re-reads `sync_account.head` every 1.5 s (for wait=25) or every 3 s (for wait=55). That is at most ~20 D1 reads, under the free plan's 50-query limit.
- Each call records `acked_seq = after` for the device.

**Batch push:** `POST /batch {ops:[{recordId, entityId, expectedRevision, tombstone, payload}]}` takes up to 50 ops and returns `{head, results:[{revision}|{conflict}]}`.
- Each op keeps today's conditional-write rule.
- `seq` is assigned inside the same D1 batch (a transaction): `INSERT OR IGNORE sync_account`, then `head = head + 1`, then an upsert with `seq = (SELECT head…) WHERE revision = expected`.
- `PUT /records` also assigns `seq`, so the Android contract is unchanged.

**Kill switch and version gate:**
- `SYNC_PAUSED` (env) or `sync_account.paused` makes `/changes` and `/batch` return 503 `{paused:true}`.
- `MIN_DESKTOP_VERSION` makes older builds get 426, based on the `X-MP-Client: desktop/<ver>/<arch>` header.

### 3.2 Encryption
- Records are sealed with the DPAPI-cached vault key. The revision inside the authenticated metadata is `expectedRevision + 1`; after a 409 the laptop re-seals.
- **Entity ids are opaque** so tmux session names never reach the server:
  - Tab id is `"t" + hex(HMAC-SHA256(K_id, "tab\0" + host + "\0" + tmux))[0..32]`, where `K_id = HKDF(vaultKey, "mp-sync-v1 entity-id")`. It is the same on every laptop, so the same tmux session deduplicates automatically.
  - Workspace and group ids are random (`ws-`/`g-` plus 16 hex characters). Setting ids are `"p"` plus an HMAC of the key name.
- The device key lives in a new file, `sync-device.dat` (DPAPI). Device name and architecture travel only inside an encrypted `device` record.

### 3.3 Live updates and battery
- **Push:** `saveSession()` (10590) and `publishInboxState()` (50011) arm a one-shot `TIMER_SYNC_DIFF` (id 36, 500 ms). No periodic timer is added.
- **Pull:** one long-poll thread. It waits 25 s in normal mode and 55 s when `powerModeForTimers()` (371) reports saving or deep idle; Cloudflare's idle cutoff is 100 s.
- **Connection reuse:** a persistent WinHttp session per sync thread keeps TLS alive. Today's `httpsBearerRequest` opens a new session per call.
- **Sleep:** `PBT_APMSUSPEND` (57988) stops both sync threads; resume polls immediately.
- **Errors:** back off 1, 2, 5, 15 and 60 s.
- **Cost:** about 144 requests per hour per idle laptop. That is far inside the Workers (100k requests/day) and D1 (5M reads/day) free tiers for 3 laptops plus a phone.
- **Why long-poll:** 3 s polling would mean 1,200 requests and radio wake-ups per hour for the same latency. A WebSocket needs a Durable Object, a WinHTTP WebSocket client and reconnect code, and the long-poll contract lets us upgrade the server side later with no client change.

### 3.4 Desktop threads
- Two sync threads, one for polling and one for pushing, handle only network and crypto. The UI thread owns all app state.
- Queues use the `enqueueNotification` mutex pattern (47004). Results come back as `WM_APP_SYNC_INBOUND` (WM_APP+145) and `WM_APP_SYNC_STATUS` (+146).
- One sync process per APPDATA: the single-window host process takes the named mutex `Local\ZigShell-sync-<hash(APPDATA)>`, following the pattern of `lockWorkspaceRegistry` (8365).
- DEV builds don't sync unless started with `--sync`, and then use their own `sync-state-dev.json` and device.

## 4. Data model
### 4.1 What syncs, what stays on each laptop
**Tabs:**
- Sync: tmux tabs that have a session name.
- Per laptop: cmd, pwsh, bash and git-bash tabs; plain ssh tabs without tmux; local Claude tabs.

**Per-tab fields that sync:**
- Manual name, a display label hint, workspace, group and position.
- Pinned, locked, muted and Chat View on/off.
- Agent kind, plus the Claude session id and remote cwd (needed for archive restore).
- State (open/snoozed/archived) with due time, filed (inbox `e`), and a read watermark.

**Per-tab fields that stay per laptop:** pid, wake_id, keep_alive, favicon path, browser pane fields (bon/burl/bnat/bsplit/kaw), full_width, preview and activity. `needs_attention` is derived locally (the read watermark syncs instead). `la` is sent only once, as a creation hint.

**Workspaces:** name, order and snoozed-until sync. The active pill, window placement and registry restore flags stay per laptop.

**Groups:** name, colour, collapsed state, order and workspace sync.

**Settings that sync:**
- Theme (including `theme-mode.txt`), console font size override, Chat View text size.
- Chat View mode (plus the everywhere on/off), voice speed, voice always-listen.
- Tab sort mode, sound, ETA numbers and progress.
- Hide pills, collapsed sections, and the sidebar status card.

**Settings that stay per laptop:**
- UI scale; sidebar hidden, collapsed and width.
- Mobile mode, power profile.
- Browser engine, exe paths and profile; browser auto-suspend.
- Window positions, changelog-seen, palette usage counts, chat autocomplete recent list.

**Custom commands and snippets:** commands for tmux and ssh sync because their paths are remote. Commands for cmd, pwsh and bash stay per laptop because their paths are local. Snippets sync.

**Hosts:** the three hosts are built into the app, so all laptops already agree. The alias-to-server-and-key mapping lives in each laptop's `~/.ssh/config` and never syncs. The host id in records is `tmuxHostLongLabel()`. Host records wait until hosts become editable (Phase 4).

**Keys and secrets:** never synced. A future vault "keys" record would need its own threat model.

### 4.2 Records (new record ids; adding ids doesn't break existing clients)
Bodies are canonical with a pinned field order, and unknown fields are preserved when a record is rewritten.
- `tab`: `{"v":1,"host":"hetzner","tmux":"claude-x","ws":"ws-…","name":null,"label":"Fix login","agent":1,"csid":null,"cwd":"/srv/app","pinned":false,"locked":false,"muted":false,"chat":false,"la":1727500000,"pos":"a0","group":null,"state":"open","dueAt":null,"readAt":0,"filed":false}`
- `tabWorkspace`: `{"v":1,"name":"Hypertask","pos":"a1","other":false,"snoozedUntil":null}`
- `tabGroup`: `{"v":1,"ws":"ws-…","name":"Review","color":3,"collapsed":false,"pos":"a2"}`
- `pref`: `{"v":1,"key":"theme","value":"amoled"}`
- `device`: `{"v":1,"name":"LAPTOP2","arch":"arm64","app":"0.28.66x"}`
- `command` and `snippet` come in Phase 3.

### 4.3 Local state file
- `%APPDATA%\ZigShell\sync-state.json`, written atomically with `writeFileAtomicW` (7943).
- It holds: deviceId, accountId, cursor; per entity its revision, hash and base body; an id map for pills and groups matched at first sync; local-only overrides; the paused flag; the last error.
- Local files stay the source of truth: the app starts only from `session.json`. Applying a remote change runs `saveSession()` first and then writes the new base, so a crash in between only re-pushes an identical value.

### 4.4 Merge rules
**Push and pull:**
- On push, `expectedRevision = base.revision`. A 409 triggers `merge3(base, local, remote)`, a re-seal and a retry, at most 5 times.
- On pull, if `remote.revision > base.revision`, the laptop merges and applies; if the merged result differs from remote, it pushes the result.

**Per-field logic:** if local equals base, take remote. If remote equals base, take local. If both changed, use the field rule:
- name, label, ws, group, pos, pinned, muted, chat, colour, collapsed and setting values: the later write to reach the server wins (the laptop that rebases). The laptop that lost shows a one-line notice.
- locked: true wins.
- readAt and la: the maximum wins.
- state: archived beats snoozed or open; otherwise the later write wins. The due time travels with the state.
- Delete vs a concurrent edit: the delete wins, unless the tab is locked on the receiving laptop. That laptop then re-creates the record.
- Position ties are broken by entity id.

**First sync (union only, nothing is deleted):**
- Tabs are matched by id. Server values win, except that a manual name beats no manual name and pinned/locked are combined (true if true on either laptop).
- Pills are matched by case-insensitive trimmed name; "Other" always maps to the fixed id `ws-other`.
- Groups are matched by (workspace, name).
- Settings: server values win, and the preview can keep this laptop's settings instead.

### 4.5 Scenarios
- **Both laptops rename the same tab:** the second push wins, and the first laptop sees the new name within about 2 s with a notice. Unrelated edits (A pins, B renames) both survive.
- **One laptop closes a tab the other is using:** the close wins. If that tab is on screen on the other laptop, the close waits until the user switches away, with a "Keep open everywhere" option that re-creates it. Ctrl+Shift+T still works.
- **Both reorder:** positions are fractional keys, so moves of different tabs both apply. If both moved the same tab, the later move wins.
- **A workspace is deleted while another laptop moves a tab into it:** the tab lands in "Other" on every laptop.
- **A laptop is offline for days:** it merges field by field against its stale base. Remote closes go through the inbound guard (4.6). After more than 14 days offline it rejoins with first-sync union rules, so it can add but never delete.
- **A tmux session is killed outside the app:** the laptop whose tmux listing (`fetchTmuxSessions`, 19439) shows it missing for 10 minutes closes the record everywhere.

### 4.6 Deletes come only from explicit intent
- Explicit close actions call `noteSyncCloseIntent(idx)` before closing:
  - Ctrl+W (`WM_APP_CLOSE`, 54743).
  - Ctrl+Shift+W (54752, `endActiveTmuxSession` 16526).
  - Archive (`archiveTabAt` 16404).
  - The tab close button, context-menu Close, and inbox archive.
- Tabs that disappear because ssh exited (a clean-exit `closeShell` in the shell-exit handler, e.g. tmux detach or a session killed from another laptop), failed restores, or hitting the tab cap produce no sync write.
- **Guards:**
  - A batch in either direction that would close 5 or more tabs and at least 30% of synced tabs pauses and asks first.
  - Nothing is deleted during restore, or before the first pull after startup.

## 5. Applying remote changes live
All remote changes apply on the UI thread with `g_sync_applying = true`, so the diff never echoes them back.
- **Create a tab:** build a SavedTab and call `preserveFailedRemoteSavedTab` (10639) with a new `parked` flag on `Shell` (2167), persisted as `"pk":true`.
  - No ssh, no focus change. The `la` hint places it in auto-sort where the origin laptop has it.
  - Clicking it attaches with plain `tmux attach` through `respawnShellInPlace`. It never goes through the resurrect or launch-command paths, so no agent is started or resumed.
  - `reconnectSshTabsAfterResume` (19161) and restore skip parked tabs.
- **Close a tab:** `closeShellRemember(idx, true)` (21962). This kills only the local ssh.exe, never `killRemoteTmuxSession` (16058). Locked tabs are kept and their record re-created; the tab on screen is closed later.
- **Rename:** set the name and `name_source = .manual`. Never call `syncShellDisplayNameSurfaces` or `syncRemoteDisplayNameForShell`.
- **Pin, lock, mute, Chat View:** set the flag, then `invalidateSidebar` (31683) and `publishInboxState`.
- **Move between pills:** change `shells[i].workspace`; never change `g_active_workspace`.
- **New pill:** a new `addSyncedWorkspaceSlot(name, id)`, not `newWorkspace`.
  - The limit is 9 pills (MAX_LWS); any extra pills stay unshown with a notice.
  - Then call `syncInProcessWorkspacesToRegistry`.
- **Remove a pill:** close its synced tabs, move its local-only tabs to "Other", then `removeWorkspaceSlot`.
- **Order (Phase 2):** sort by the position key using `moveShellToIndexWithGroup` (4117).
  - Local-only tabs stay after their previous synced neighbour.
  - Auto-sort (`g_tab_sort_auto` 2338, `layoutRows` 4647) is untouched. Sync changes only the underlying array order, which matters in manual mode and as the last tie-break.
- **Busy UI:** while a drag, rename box, the Ctrl+K palette or a context menu is open, structural changes queue and apply on `TIMER_SYNC_APPLY` (37, 250 ms) once idle.
- **Snooze and archive (Phase 2):**
  - A remote tab snooze parks the tab and records a reminder; the due time wakes it on every laptop.
  - A remote workspace snooze hides the pill and parks its tmux tabs, but never closes this laptop's local tabs.
  - A remote archive closes the tab and adds the `archive.json` row.
  - Restoring from archive uses the `has-session`-guarded resurrect, so two laptops restoring at once still start only one agent.
- **Claude twice:** both laptops attach to the same tmux process, so it is the same conversation. Local Claude tabs are per laptop and are never synced (`workspace_snooze.claudeResume` stays local).

## 6. tmux side
- On hypertask-vps (checked read-only): tmux 3.4 with `window-size latest` (the default since 3.1) and `aggressive-resize off`.
- **Recommendation: `latest`.** The window follows whichever laptop was typed on last. `smallest` wastes the bigger screen and `largest` crops the smaller one.
- Set it explicitly in `~/.tmux.conf` on vps, contabo-uk and inne-cro-vps:
  ```
  set -g window-size latest
  setw -g aggressive-resize on
  ```
  Apply it to running servers with `tmux set -g window-size latest`, and confirm `tmux -V` is at least 3.1 on contabo-uk and inne-cro-vps. This is a one-time server step, not app code.
- **Optional:** a one-time warning in the app if `tmux show -gv window-size` isn't `latest`.

## 7. Rollout
**Turning it on:**
- Ctrl+K "Turn on sync on this laptop" (palette offsets 9102 and up).
- It chains the Sync 4 sign-in and vault unlock if needed, registers the device, shows the preview, and then stays on across restarts.

**First sync:**
- Laptop1, with an empty server, sees: "Upload 42 tabs, 6 workspaces, 14 settings."
- Laptop2 sees: "From your other laptop: 38 tabs, 4 workspaces. From this laptop: 3 tabs, 1 workspace. Same tmux session on both: 4. Settings that differ: 5 (using the other laptop's)."
- Buttons: Yes = merge and turn on; No = merge but keep this laptop's settings; Cancel. A Details button writes `sync-preview.txt` and opens it.

**Safety around the first sync:**
- Before applying, back up `session.json`, `reminders.json`, `archive.json` and `windows.json` as `*.pre-sync-<date>.json`, keeping 3 copies.
- Round-trip proof: after the first push, download everything again, decrypt it and compare it with local state. Any mismatch pauses sync with a message.

**Dry run:** Ctrl+K "Preview sync changes" works at any time and writes nothing.

**Kill switches:**
- On the laptop: the Pause toggle; a `%APPDATA%\ZigShell\sync-off` file; the `--no-sync` flag.
- On the server: `SYNC_PAUSED` or a per-account paused flag makes laptops stop and re-check every 15 min. `MIN_DESKTOP_VERSION` cuts off a bad build.

**Surfaces:** Ctrl+K rows, F1 `SHORTCUT_ROWS` (33849), `openwiki/operations/keyboard-shortcuts.md` "Sync" section, and `CHANGELOG` bullets (32526).

**QA without Valentin:**
1. `zig build test`: pure tests for `src/sync_engine.zig` on Linux. They include a 3-laptop simulation against an in-memory server with D1's 409 rules, using random interleavings (create, close, rename, move, pin, going offline) and asserting all laptops converge. They also cover the guards and first-sync union cases: disjoint states, overlapping sessions, pills matched by name, more than 9 pills.
2. Worker vitest: seq ordering, long-poll waking on a write, batch with conflicts, device register and revoke, kill switch, minimum version, account isolation.
3. A Linux-native harness (`tools/sync-sim`, std.http) running 2–3 simulated laptops against a staging Worker (`sync-staging.multiprompt.dev`, separate D1) with real crypto. This avoids wine, whose missing RNG already makes crypto tests skip (sync_protocol.zig:926).
4. A Windows GUI smoke test with two DEV instances using different APPDATA folders (`$env:APPDATA='C:\mp-qa\a'; zigshell-dev.exe --single-window --sync`), pointed at staging.
   - Sign in once, then copy the DPAPI token file into the second APPDATA (same Windows user); each instance then registers its own device.
   - Script: create, rename, close the focused tab, move a pill, pause, trigger the kill switch. Measure A-to-B delay from `debug.log` (target under 3 s).
   - Run it on a Windows VM or a GitHub `windows-latest` / `windows-11-arm` runner whose ssh config points `vps` at a throwaway tmux container. Not on Valentin's laptop, where DEV next to stable breaks Alt+Tab grouping.

  - Ctrl+K Turn on/Pause, Sync now, Preview and a richer Status; F1 row, docs, changelog.

**Phase 2: everything on Valentin's list (medium-large, ~1,500 lines):**
- Tab and pill order, groups, and settings.
- The snooze, reminder and archive states, including workspace snooze.

**Phase 3: N laptops (medium, ~1,000 lines):**
- A device list with "remove laptop".
- "Keep on this laptop only" for a tab or a setting.
- Custom commands and snippets.
- Standalone multi-window windows.
- Rejoin rules for stale laptops.
- Server-side cleanup of deleted records (once every laptop has seen them) and a Reset sync action.

**Phase 4 (later, only if needed):** Durable Object wake-ups, editable hosts with host records aligned to Android, and parity with Android's `sessionState`.

## 10. Bugs found outside the ticket
**10.1 The second laptop gets no blue dots or spinners, and wastes SSH logins.**
- `maintainTunnelKeeper` (12649) forwards server port 19548 with `ExitOnForwardFailure=yes`. Only one laptop can hold that port.
- The other laptop's tunnel process exits and restarts every ~5 s: `retry_after` is 5000 ms and `TIMER_TUNNEL_KEEPER` fires every 2 s (6038). That is a new ssh login to each server every few seconds, all day.
- The server-side hooks write only to `localhost:19548`, so notifications reach one laptop.
- **Fix:**
  - Each laptop forwards its own socket: `-R /tmp/mp-notify-$UID/<deviceId>.sock:127.0.0.1:<port>` with `StreamLocalBindUnlink=yes`.
  - A tiny user service on each server listens on 19548 and copies every notify line to all the sockets. zsb request/response messages go to the newest socket only.
  - The hooks stay unchanged.
- **Check first:** laptop2's `debug.log` should show repeated "tunnel-keeper: started".

**10.2 New tmux session names could collide across laptops.**
- Alt+T and Codex name sessions `term-<GetTickCount64 hex>` and `codex-<…>` (18550/18623).
- If two laptops ever produce the same name, `new-session … 2>/dev/null; attach` would join the other laptop's session, and the Codex path would type `codex` into it.
- **Fix:** add 4 random hex characters to the name.
